# 版本与兼容性

LogoDock 同时提供静态网站、原始素材和 JSON 索引，目前不发布 npm 图标包。仓库版本、素材内容和元数据结构的版本分别维护。

## 数据维护来源

- `logo/<id>/metadata.json` 与登记的原始文件是维护来源。
- `index.json` 和 `docs/catalog.md` 由 `npm run build:index` 生成，不手工编辑。
- `static/`、`_site/` 和 `.svelte-kit/` 是本地构建产物，不提交。
- `src/` 内部函数、组件拆分和测试辅助模块不是公共 API；调整它们时仍须保留网站行为与既有链接。

## 品牌 ID 与文件路径

已经公开的品牌 ID 和 `logo/<id>/<asset-file>` 路径应保持稳定，不能只因修改中文名称、网站分类或内部目录整理而改名。

- 新增品牌、版本和格式使用新的稳定路径，保留已有文件的来源与使用条件。
- 已被替代且无独立用途的冗余文件，直接删除图片及元数据登记，同步更新默认、分组、索引、资源清单和数量；历史图片及来源通过 Git 追溯。仅在明确存在外部引用时单独评估兼容措施，不为假设中的引用保留冗余。
- 旧详情 `?asset=<file>` 和旧首页 `?brand=<id>&asset=<file>` 继续支持已收录文件的选择，已删除或无效的文件参数回到品牌默认，不提供逐文件替代映射。删除后的旧图片直链返回 404；没有 JavaScript 时只提供当前默认素材和现有文件下载入口。
- 更新文件内容时同步摘要、字节数和受影响的来源记录，并在变更记录中说明。同一路径的当前内容可能变化，固定完整 commit SHA 的链接用于引用旧快照。
- 必须重命名或删除文件时，列出旧路径、原因及替代路径；没有替代资源时明确说明。资源纠错或权利请求需要移除文件时，记录实际处理结果，不承诺永久保留有问题的资源。
- 不通过静默改写索引字段、品牌 ID 或路径制造不兼容变化。

## 元数据结构

当前 `schemaVersion` 为 `4`，它表示元数据结构，不等同于 `package.json` 的项目版本。

- 增加必填字段、删除字段、收紧原本允许的值或改变字段含义，需要评估为不兼容变化，提供迁移方式并更新相应结构版本。
- 新增可选信息需让旧记录仍可校验，并检查索引、录入工具、网页和测试是否一致。
- 文件可选字段 `display` 为 `primary` 或 `alternative`，仅区分主要与有用备选层级，旧记录省略时按 `primary` 处理，在 v3 引入，v4 继续支持。品牌 `defaultAsset` 必须仍在登记中且不能指向备选文件；调整时同步复核默认文件、同稿分组和旧说明。
- v4 的 `categories` 使用 `src/lib/catalog-taxonomy.mjs` 中的叶级行业 ID，并支持可选的跨行业 `topics`。v3 的开放标签需按品牌业务迁移到对应叶级行业，再将 `schemaVersion` 改为 `4`。已有素材路径与逐文件登记继续沿用。
- 后续新增行业或专题时扩展分类字典，补充中文名称和业务范围，同步相关记录与校验。增加可接受的分类 ID 可沿用 v4。旧目录 URL 中已使用的行业参数会解析到当前分类入口。
- Schema、运行时校验器、录入工具与消费者必须在同一变更中保持一致。结构升级时明确旧记录的迁移要求，不依据文件名推断数据版本。

## 发布记录

面向使用者的变化记入根目录 `CHANGELOG.md` 的“未发布”部分，包括重要交互、素材增删、路径变化及数据契约变化。该文件也是站内 `/changelog/` 页面的唯一内容来源，页面构建时读取已归档批次。

网站成功部署后，对照 GitHub Pages 部署记录核实对应提交及北京时间日期，将已上线内容归档为 `## YYYY-MM-DD · 更新标题`，按日期倒序排列。同一天的多个批次按正文中的先后顺序展示，每个批次附上部署记录链接。`## 未发布 · 更新标题` 保留待发布内容，公开页面展示已归档批次。

批次内使用 `### 新增收录`、`### 素材更新`、`### 体验改进与修复`、`### 引用变化` 按实际内容分类，通常归纳为 2–5 条用户可感知的变化。品牌使用 `[品牌名](logo/<id>/)` 链接，旧路径、删除原因和替代路径放在“引用变化”中，页面将其折叠展示。正文支持段落、无序列表、表格、行内代码、加粗和 Markdown 链接。

正式建立版本标签或 GitHub Release 时，在批次标题中附上对应版本号，并同步 `package.json` 和 lockfile。`0.x` 阶段同样需要说明破坏兼容性的变化，不能把当前包版本号当作已经发布的证明。

部署网站与发布仓库版本是不同操作。主分支的 Pages 发布必须先通过代码、数据、生成文件一致性、构建、Node 测试和浏览器回归；本地检查成功不代表远端发布已完成。
